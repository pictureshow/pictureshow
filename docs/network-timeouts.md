# API timeout policy

Core's `ApiTimeouts.REQUEST_MILLIS` gives each API call **30 seconds**, including reading and decoding the response. It covers password and remembered sign-in, each Quick Connect request, catalog and search, preferences, PlaybackInfo and session reports. Quick Connect's five-second poll interval and server-issued code expiry are separate from each request deadline. Core does not retry a call after its deadline expires; the viewer can retry after the resulting error. Caller cancellation is propagated.

Automatic port discovery keeps **4 seconds per public-info candidate**, preserving HTTPS-first sequential fallback and base paths. Scheme-less input tries at most four candidates (16 seconds if all accept a connection and stall); an explicit scheme and port tries one with the normal **30-second** API deadline. Invalid input makes no request. This short discovery deadline is intentional: enter the full server address including its port to avoid irrelevant probes and allow a slow public-info response.

The Ktor transport owns only the **3-second connect timeout**. `jellyfinApiTransport()` disables Ktor request and socket timeouts, preventing shorter engine defaults from overriding core's deadline. Apply it to any transport supplied to these clients. Core still imposes a finite deadline when a connection is accepted but headers or body never arrive. Transport errors become connection failures; core deadline expiry says the server took too long and to try again. Do not apply this policy to the separate Media3 media data source.

## Sources checked 2026-10-23

- [Jellyfin SDK HttpClientOptions](https://github.com/jellyfin/jellyfin-sdk-kotlin/blob/88f916be946d06902df96af39864b61e9c75698b/jellyfin-api/src/commonMain/kotlin/org/jellyfin/sdk/api/client/HttpClientOptions.kt): 30-second request/socket defaults and 6-second connect default. Our 30-second API budget follows this precedent; keeping our existing 3-second connect limit is a product choice for responsive address entry.
- [Official Android TV dependency wiring](https://github.com/jellyfin/jellyfin-androidtv/blob/56c6fc44dc4bd1898ab25af030df575cd25f4618/app/src/main/java/org/jellyfin/androidtv/di/AppModule.kt): creates the API client with the default SDK HTTP options.
- [SDK recommended-server discovery](https://github.com/jellyfin/jellyfin-sdk-kotlin/blob/88f916be946d06902df96af39864b61e9c75698b/jellyfin-core/src/commonMain/kotlin/org/jellyfin/sdk/discovery/RecommendedServerDiscovery.kt): uses a separate 3.5-second public-info timeout. We retain the existing 4-second budget when probing alternative ports, rather than lengthening every candidate attempt. A single fully specified endpoint gets the API budget.
- [Jellyfin JavaScript API client](https://github.com/jellyfin/jellyfin-apiclient-javascript/blob/0595869949a6da0b9e62f6a2c4a4e349f5282109/src/apiClient.js): `fetchWithFailover` sets 30 seconds for API requests.
- [Ktor timeout documentation](https://ktor.io/docs/client-timeout.html): explains connect, request and socket limits and their engine support. Core's coroutine deadline also covers body consumption and is exercised with virtual-time MockEngine tests; app transport tests verify the actual OkHttp connection limit and slow responses.

These are network API limits, not a promise that an entire screen composed of several sequential calls completes within 30 seconds. A deadline cancels the call and returns an error; core does not start a fresh password sign-in or code exchange automatically. The app retains OkHttp's standard connection recovery and HTTP follow-ups within that deadline (for example a server 408 response may be retried). This policy does not promise exactly-once server execution: the server may have accepted a request whose response was lost.
