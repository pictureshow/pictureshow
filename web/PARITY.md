# Web Android-parity ledger

Reference: the 94 Android-implemented table IDs plus the rc28 prose-defined PLAY-24 in [`spec/features`](../spec/features/README.md), integrated from the pinned Android TV and additive touch snapshots. This ledger records the web implementation and its evidence; it does not promote Android’s explicitly unimplemented inventory into web scope.

Status categories are disjoint:

- **Implemented**: the browser feature/policy exists. Evidence and remaining unproved acceptance criteria are explicit in its row.
- **Platform-dependent**: the browser offers the stated native alternative or an honest unavailable state; an Android-only API/capability is not claimed.
- **Gap**: a required portable feature is absent, with a reason.

**Verification is independent of implementation.** Here **Verified** means that each of the **80 portable Implemented IDs** has named automated policy/UI primary-behavior evidence. It does not mean that every subcriterion, human screen-reader utterance, physical remote/phone interaction or media-format/output combination has been accepted. The feature rows retain those narrower limits explicitly. The 15 Platform-dependent IDs have the stated alternative/unavailable behavior and evidence; they are not counted as fully reproduced Android APIs. A shared-vector pass is policy evidence, not full UI/device acceptance.

Totals: **80 Implemented · 80 primary-behavior Verified · 15 Platform-dependent · 0 portable feature Gap = 95 feature IDs**. Verified is an overlapping evidence count, not a fourth implementation-status category.

**Engine qualification (Follow-up 4):** the complete **79-case browser suite passed in Chromium, WebKit and Firefox on Linux: 237/237 checks**, with no retries, skips or exclusions. This includes the keyboard-only paths, real fixture video, caption timing, axe and recovery geometry at TV, desktop, narrow tablet and phone widths. **88 unit tests and all 611 shared vectors passed**, plus six web background-policy projections of the `visibility-play` vectors (617 vector-suite checks). The runner reads this repository’s `spec/` by default and retains `PICTURESHOW_SPEC` for an isolated runner. Complete Android profile inputs remain hypothetical reference-policy evaluation; actual web playback uses browser capability probes. Runtime dependency audit reported zero vulnerabilities. Earlier macOS Chromium/WebKit qualifications remain historical; the rc28 whole-suite qualification is Linux, plus the fresh macOS Chromium live runs in L3 and L4. The macOS Firefox audio-backend limitation was not reclassified as a browser pass.

**Historical Follow-up 1 live qualification (L1):** all three engines passed same-origin HTTP and cross-origin HTTPS private-server playback, **six mode/engine runs**. These exercised real video at 1280×720, Audio Off and restoration, pause/seek/resume, start/progress/stop reports and text cues; Chromium also completed Quick Connect sign-in. HTTPS used a local test certificate explicitly accepted by automation. **Browser-trusted public TLS and HTTPS-app→HTTP-LAN access remain unproved.** Query authentication uses the dedicated viewer token, never an administrator key.

**Review qualification (V1):** historical Opus 5.5 medium screen-family comparisons establish the accepted Android-like baseline. Follow-up 3 adds an Opus recovery-state review at TV, desktop, 600 px tablet and phone widths, plus live-player caption review and desktop/phone review of a failed item read while progress saving remains pending. Review findings drove recovery placement/copy/held-name corrections and subtitle boundary/overlay placement fixes, each with browser checks. Luna high independently reviewed the rc28 runtime and the subsequent fixes. Images establish appearance, while named tests establish the measured geometry and state transitions; neither claims actual screen-reader speech.

The specific feature rows distinguish implementation from those unproved subcriteria.
