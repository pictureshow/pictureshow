# Shared playback control and queue (launch draft)

**Status: Kotlin control/queue reducers and local-video owner boundary implemented; transport integration, Apple/web ports and device acceptance remain unproved. No row is marked passing on device.** Drafted 2026-11-03 against `de505e2`. Applies to Android TV/Google TV/Fire OS, Android phone/tablet, iPhone/iPad, Apple TV and web. Android defines the reference after implementation; this draft defines the intended new behavior. All [shared input, accessibility and recovery rules](shared.md) apply.

Protocol source: [versioned API contract](launch-api.md). These are original Pictureshow policies; Jellyfin session relay and SyncPlay are different transports. [Plex Companion](https://support.plex.tv/articles/203082707-supported-plex-companion-apps/) documents controller/receiver roles, with a warning excluding newer mobile apps. Direct Plex article retrieval was blocked; its official indexed excerpt and prior intent inventory support this statement. This supports the intent, not a claim that every current Plex client supports every role.

| ID | Behavior | Acceptance criteria |
|---|---|---|
| CTRL-01 | One playback owner, identified by server/viewer/device/session/viewing generation and target kind. | Local player, Jellyfin target, Cast receiver and AirPlay route are distinct. Only the rendering owner reports playback; a controller cannot create a second watched count. AirPlay remains the originating player's viewing. Late events from a replaced owner cannot change current playback or a different viewer. **Status:** Kotlin identity/report/handoff policy implemented; local video boundary installed. Remote/Cast/AirPlay reporting and device acceptance unproved. |
| CTRL-02 | Commands enter one serialized intent reducer with desired play state, item/queue entry, bounded ticks and current generation. | Pause twice stays paused; a held key does not toggle twice. Relative seeks accumulate against pending target per PLAY-07. Reject stale targets, invalid numbers, unsupported commands and wrong server/account. Native/system/remote input uses the same freshness guards. The accepted Android video player is one owner adapter; retain its internals and all existing PLAY vectors/regressions unchanged. **Status:** Kotlin serialized desired-command reducer implemented. Accepted local video inputs retain their existing path; new controller dispatch wiring and system/remote convergence unproved. |
| CTRL-03 | Target handoff has selecting, connecting, preparing, active, disconnected, returning and failed states. | Pass requires each separately reported subcriterion CTRL-03a through CTRL-03d; a partial pass does not pass CTRL-03. **Status:** Kotlin handoff state/effect policy implemented, including a–d. Actual two-output timing and receiver behavior unproved. |
| CTRL-03a | Preparing preserves local intent. | Keep local queue, current entry, position and pause intent until the handoff commits or the viewer cancels. **Status:** Kotlin immutable handoff intent implemented; physical transfer unproved. |
| CTRL-03b | Only one output becomes audible during handoff. | Pause local output before requesting remote playback. Commit ownership only after matching receiver readiness and observed position; a stale generation cannot commit. **Status:** Kotlin pause-ack/readiness commit guards implemented; audible single-output proof unperformed. |
| CTRL-03c | Failed handoff is recoverable. | Retain paused local intent and show Resume here after preparation failure or timeout; network loss cannot automatically start local playback. **Status:** Kotlin failed/timeout recovery policy implemented; Resume here UI/transport unproved. |
| CTRL-03d | Return here handles uncertain remote Stop. | Request remote Stop before local Play; if unconfirmed, explain that remote playback may continue and require an explicit viewer choice before starting local output. **Status:** Kotlin uncertain-Stop explicit-choice policy implemented; remote/local output timing unproved. |
| CTRL-04 | Commands expose sent, confirmed, rejected or unknown result. | HTTP 204 is dispatched, not Played. Require a matching observed state within 5 s for ordinary control; then show not confirmed and Refresh. No blind replay of PlayNow, toggle, relative seek or queue insertion after a timeout. A refreshed desired Pause may be sent deliberately. Delayed acknowledgment cannot confirm a newer command. **Status:** Kotlin sent/observed/timeout/denial reducer implemented; remote observation correlation and Refresh UI unproved. |
| CTRL-05 | Session capabilities and authorization drive visible actions. | Never advertise unsupported media, track selection, volume, seek, queue edit or navigation. Server denial removes stale control rights. Remote target inherits its own signed-in viewer's permissions; no controller token is forwarded to a TV. Same-server item IDs cannot address another server. **Status:** Kotlin capability/account/denial guards implemented; visible actions and target auth adapters unproved. |
| CTRL-06 | Route/report ownership survives backgrounding and reconnect. | Controller backgrounding does not stop its receiver. Local video retains PLAY-24 pause policy. Explicit audio playback follows MUS-04. Reconnect obtains current target state before enabling mutations; old queued commands expire rather than replay. Stop/release only this viewing's encoding/live stream. **Status:** Kotlin background/reconnect policy implemented; accepted video lifecycle retained. Remote/audio/native OS integration and scoped live cleanup unproved. |
| CTRL-07 | Control modes compose without competing clocks. | An attached Jellyfin TV participating in SyncPlay turns its transport commands into group requests. Launch Cast/AirPlay route selection requires explicit Leave group before casting; cancel retains group/local playback. No launch external-route SyncPlay claim. Later external-output synchronization requires separate measured qualification under SYN-PD03. **Status:** Kotlin group/route routing decision implemented; SyncPlay transport, explicit-leave UI and external route adapters unproved. |
| CTRL-08 | Now playing is reachable throughout browsing, with target name, title, state and Stop/disconnect actions. | Mini-player opens full controls without creating playback. Disconnect controller leaves remote output running with explicit copy; Stop ends it. Start another local title while remote output runs requires a deliberate destination choice. Back restores opener/scroll; permission/loading/error changes retain readable status and focus. |
| CTRL-09 | Credentials, discovery and diagnostic data have explicit ownership. | Discover on viewer request; no continuous LAN scans or third-party Cast web script before enablement. Logs/export contain fixed outcome categories, relative times and synthetic/session-local IDs, never media URLs, auth, server filesystem paths or private device addresses. Permission refusal has a usable alternative. |
| CTRL-10 | Token-bearing transport surfaces are disclosed and redacted. | Prefer Authorization headers on native HTTP and web/receiver media request hooks that support them. Browser WebSocket /socket query auth, returned transcode URLs, AirPlay media URLs, progressive Cast loads and Apple offline packages can require query tokens. Privacy copy names receiver/package and server/reverse-proxy log exposure. Pictureshow logs, diagnostics and exports redact entire credential-bearing URLs; no promise of redacting external logs or exported original files. |
| CTRL-11 | Temporary device sessions have bounded lifecycle. | Use stable receiver/server/viewer or download-set device identity, never a fresh untracked identity per retry. Revoke temporary sessions with POST /Sessions/Logout authenticated as that session at their defined end/sign-out. Offline failure keeps a private durable pending-revocation record and reports pending status; retry on authenticated reconnect before provisioning another session for that identity. Successful cleanup removes pending secret material; do not accumulate live sessions or device records across repeated cycles. **Status:** Kotlin stable-identity and revocation lifecycle policy implemented. Private durable record storage, real logout and repeated server-cycle proof unperformed. |
| QUE-01 | A queue holds ordered entry IDs, media IDs, current entry, history, repeat, shuffle permutation and revision. | Two copies of the same track are distinct entries. Use exact signed 64-bit ticks; web serializes ticks beyond safe Number range as decimal strings at its adapter boundary. Changing account partitions saved queues; no credentials in a queue. **Status:** Kotlin queue identity/context/int64 model implemented; platform persistence and ports unproved. |
| QUE-02 | Play now replaces queue with the selected ordered context; Play next inserts the selected block immediately after current; Add to queue appends, ahead of any automatic continuation (a series' remaining episodes the server attached): what the viewer added plays in the order added, and the continuation resumes after it. | Preserve block order and intentional duplicates; a title the viewer names replaces its copy in the upcoming automatic continuation, so it plays once, at the added place. Shuffle mixes within added and automatic, keeping added ahead. Repeated distinct Play next operations are last-in-first-next; one operation replayed in the same local command generation is deduplicated. If no current entry, insert at zero and remain stopped until deliberate Play. Server dispatch with uncertain result is not automatically retried. **Status:** Kotlin ordered block insertion/dedup/stopped policy implemented; server mutation adapters unproved. |
| QUE-03 | Remove/move/clear use entry identity and a revision. | Moving before current preserves audible item/clock. Removing current selects its successor at the removed index, otherwise previous final entry; preserve playing/paused intent. Removing last stops. Clear upcoming keeps current/history; Clear all stops. A stale revision refreshes before a viewer repeats an edit. **Status:** Kotlin revision/entry edits implemented; native queue UI and persistent storage adapter unproved. |
| QUE-04 | Repeat Off/One/All and deterministic shuffle preserve context. | Natural end repeats current only for One, wraps only for All. Explicit Next ignores One; at final entry Off/One stops, All wraps. Previous at position >3 s restarts current, otherwise selects history/previous; first Off/One restarts, All wraps. Shuffle keeps current, permutes upcoming with an explicit stored permutation, and preserves visited history. Disable shuffle restores canonical upcoming order excluding already visited entries. **Status:** Kotlin deterministic permutation/history/repeat policy implemented; media continuation integration unproved. |
| QUE-05 | Playback errors do not create infinite skipping. | Automatic music continuation can skip each unavailable upcoming entry once per traversal, stating failure; stop when exhausted, even with Repeat All. Video failure never silently starts a different title. Explicit Retry is separate from auto-advance. End/next/remote callbacks consume one completion generation. **Status:** Kotlin completion/error traversal implemented; actual music/video error continuation integration unproved. |
| QUE-06 | Persistent playlist and current playback queue are separate. | Editing a playback queue does not silently change the server playlist. Save/Create/Add/Remove/Move playlist operations show server permissions, preserve entry IDs and read back actual order. Pending/unknown mutations are reconciled before retry. |
| QUE-07 | Transfer preserves queue intent across local, remote and Cast owners. | Preserve current entry, position and repeat/shuffle. Preserve selected tracks only when target advertises matching track support; otherwise show the unavailable selection before transfer and require confirmation of its replacement. Missing queue/repeat/shuffle capability is explained before replacement. A target's authoritative queue wins after attach; never overwrite it with a stale phone snapshot. **Status:** Kotlin transfer consent/authoritative-attach policy implemented; remote/receiver transfer and track UI unproved. |
| QUE-08 | Queue restoration is recoverable. | Restore per viewer after process death as paused, validate accessible items and download availability, and disclose removed/unavailable items. An offline saved queue never attempts network access. Persist before publishing a successful edit; failure retains last committed queue and offers retry. **Status:** Kotlin paused restore/filter and persist-before-publish/rollback policy implemented. Durable storage, process-death/offline adapter and disclosure UI unproved. |

## Planned vectors

The five executable Kotlin reference suites now run production reducers; Apple/web translations remain unproved. Gradle packages them with a separate strict control runner so existing PLAY tests/vectors stay unchanged. Required operations/cases:

- `session-owner`: target generations, viewer switch, stale response, duplicate report suppression, AirPlay owner retained, handoff prepare/fail/commit/return, unknown remote Stop; temporary token create/use/logout/pending-revoke with stable identities and bounded device records.
- `session-command`: desired pause/unpause, ±seek accumulation, 64-bit ticks, malformed numbers, timeout/not-confirmed, denied rights, capability removal, no replay after reconnect.
- `queue-edit`: duplicate media IDs, PlayNext block and repeated blocks, append without current, remove/move current/earlier/last, clear upcoming/all, stale revision and persistence rollback.
- `queue-order`: explicit shuffle permutation (do not depend on platform PRNG), history, repeat at EOS versus explicit Next, Previous at 2.999/3.000/3.001 s, error traversal exhaustion, queue transfer and account partitioning.
- `playback-mode`: stopped video versus explicit background audio, remote-controller background, SyncPlay command routing and Leave group before Cast/AirPlay; cancel preserves membership.

Platform-dependent: controls use the native media-session/route APIs. A browser tab cannot promise to keep receiving commands after OS suspension or closure; a TV without a running client is not a wakeable target. Such states show unavailable/reconnect, never success.
