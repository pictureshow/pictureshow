Caption text classification for PLAY-10: `IsTextSubtitleStream=true` or a case-insensitive codec in `subrip,srt,ass,ssa,webvtt,vtt,ttml,mov_text,tx3g,text,smi,sami` receives text rank. An unknown, unflagged codec keeps non-text rank; all earlier accessibility/language priorities still apply. The `caption-index` vectors in `application.json` include text/image/default, HI and forced-only comparisons. Apple/web port this selection policy, not an Android-only codec preference.

Stopped viewing (PLAY-24): Android TV/phone and native Apple playback pauses when its activity/viewing is stopped or fully covered under that platform's lifecycle policy. Android uses ON_STOP, not a transient loss of input focus. Store the pause intent in the viewing, before addressing any decoder, including before the first player exists. Preparation, server seeks, track switches and recovery may finish while stopped, but every replacement must remain paused and every Start/Progress body built in that state must report IsPaused=true. Stop does not release the viewing, send a viewing Stop, mark played or begin another item. Returning only restores visibility; it does not clear the pause latch. Only a deliberate foreground Play clears it, and background Play commands cannot do so. The clock/seek target and track intent survive. Automatic-next timers and late callbacks must recheck visibility; returning does not restart them until deliberate playback resumes. If an advance already committed its final Stop before backgrounding and reporting is still pending, cancel its automatic route, retain the completed destination/timeline and offer explicit Next/Play or Exit after return. A browser's background tab is not by itself a native stop: web chooses whether foreground is required according to its platform's background-play policy. The `visibility-play` vectors make that policy an explicit input.

Track-panel responsiveness (PLAY-08, with PLAY-05 focus return): prepare both Audio and Subtitle descriptions when the playback source metadata arrives, using a background worker (Android: `Dispatchers.Default`). Opening a chooser, playback ticks, focus changes and selection changes reuse those prepared menus. A changed source ID or stream list invalidates the generation; an older worker cannot publish its result as the newer source. An early open waits without blocking the UI and mounts a complete current-source menu once ready. A request made before the initial playback source is known follows the first real source, unless cancelled in the meantime. Back, stop/backgrounding, playback error or navigation cancels a pending open, so later worker completion cannot open an unsolicited panel. Source replacement cancels a pending open; an already open panel closes through its panel-scope handoff to its exact opener, retaining its captured rows/selection only for that handoff and refusing selections against the replacement source.

Once the track panel appears, a long list claims its selected row during initial layout; the first arrow moves from it even when a window-focus coroutine would be delayed. A later frame or window-focus return must not restore the arrival selection over a viewer's navigation. Chapters share the one-time input-focus handoff. Test a 45-row list during a transcode on a constrained TV, including idle time, keys, source replacement, pending-open cancellation, and return to the opener; unit tests alone do not establish device performance.

The executable `tracks.prepared-menu.current-source-server-index` application vector verifies the current source's authoritative selected subtitle index, including a mixed Audio/Subtitle list. It does not run a metadata worker, mount a native track window, query the native accessibility provider or deliver lifecycle/input events. Native preparation/reuse/stale-worker acceptance lives in `PlayerTrackMenuPreparationTest` and `TrackPanelResponsivenessTest`; pending Back/stop cancellation and source-change focus handoff additionally require the `PlayerScreen` native acceptance flow. Apple and web implement the same preparation, generation and cancellation outcomes using their own worker and UI mechanisms, with equivalent entry focus and modal accessibility; the Android coroutine implementation is not the portability contract.

External-text portability: Apple and web implement PLAY-22's selection, cancellation, retry and clock semantics using their native player/network layers; the Android MediaSource/Loader implementation itself is platform-specific. `external-subtitle-loading` vectors define retry delay and full-file source offset (including large clocks and counts). The loader must not consult the player's 45 s A/V stall deadline. This independence is behavioral and also requires a delayed/failing HTTP fixture test on each platform; vectors alone do not prove readiness or cancellation. Android bounds an external subtitle response to 16 MiB before parsing, treats oversize text as an isolated subtitle load failure, and retries while selected.

Platform-dependent presentation: Apple/web derive their own real codec, HDR, resolution, channel and output capabilities. Do not advertise Android FFmpeg, DTS/TrueHD/AC3 passthrough, PGS local decoding, HDMI refresh behavior or a protocol just because the Android profile supports it. Use server conversion where supported; label its result and burned-in limitations. When neither local decode nor server conversion is available, explain the unsupported format and provide Back/retry. Browsers use available native/HLS facilities and require honest network/auth capability; TV and phone use native media controls. The UI may use native player sheets while retaining these actions, state and recovery semantics.

Android panel diagnostics (`PictureshowPlayback`) record `panel-open title=<title> inActivityWindow=<bool>` once at the mounted panel's first layout. This receipt anchors panel/input timing; it does not prove the frame was presented or that input/accessibility focus reached the selected row. Track and chapter panels retain their native Dialog boundary. Their existing `panel-close title=<title> waitMs=<ms> focused=<bool>` receipt reports the activity window-focus handoff; it does not establish exact opener input or TalkBack focus. Those need native focus evidence and reader verification.

Android release diagnostics (`PictureshowPlayback`) log each subtitle choice, including open, as `subtitle-select stream=<index|off> paused=<bool> positionMs=<full-media ms> selection=<counter>` (plus item/session fields). `subtitle-cues stream=<origin index|unknown> firstCueAtMs=<full-media ms> selection=<counter>` is a receipt after applying a nonempty group to SubtitleView, once per origin per selection. The origin is captured at renderer output before queuing to the UI; it is never inferred from the current requested index. Unknown provenance is explicit. `subtitle-loaded stream=<index> attempts=<count>` is emitted once after successful selected external loading/parsing, including retries. No cue text, URL or exception message is logged; receipts prove delivery to the view, not physical projector pixels.

Playback reporting diagnostics (PLAY-20): each Start, Progress and Stop attempt emits a completion line with a viewing-local increasing sequence, report kind, full-media position, audio/subtitle indices exactly as sent (`omitted` for absent fields), and independent `automatic`/`viewer` origins captured with that body before HTTP suspends. Stop always omits indices while retaining the origins. Include the actual HTTP status if received, a fixed failure category (`http`, `timeout`, `network`, `invalidresponse`, `cancelled`, or `none`), and monotonic elapsed milliseconds. A retry is another attempt/sequence. Never log cue text, URLs, tokens, or exception messages. HTTP success proves endpoint completion, not a persisted remembered choice; compare PlaybackInfo for that claim. The `playback-report-fields` vectors define the portable snapshot fields. Android logs these in release as `PictureshowPlayback report`; Apple/web port the same report snapshot/outcome semantics using their native diagnostic sinks.

Report ordering (PLAY-20): build each body when its serialized command executes, then await that attempt before executing later commands. A queued periodic report must observe a preceding accepted viewer choice. A failed Start/Progress is not replayed as an old snapshot; the next periodic check-in (normally 10 s) or final Progress uses current intent. Stop retries once. A request deadline does not prove the server cancelled work already received, so delayed server completion or another client's concurrent save remains possible. External subtitle extraction has no role in this queue or the A/V READY gate under PLAY-22.

Android release lifecycle evidence logs `lifecycle foreground=<bool> paused=<bool> positionMs=<n>`, READY includes paused/foreground, and actual playing transitions log `play-state playing=<bool> paused=<bool> foreground=<bool> positionMs=<n>`. Report outcomes append the immutable body field `paused=<bool|omitted>` (omitted for Stop); a response to a body sent before stopping can complete later, identified by its sequence and elapsed time.

Caption default retention (PLAY-10): before applying the system caption language or ranking, retain `DefaultSubtitleStreamIndex=-1` as Off or a nonnegative default that identifies an actual subtitle stream in the selected source. A default pointing to an absent stream or to audio/video is unusable and permits caption fallback, as does null/omitted. Jellyfin does not identify whether a valid default was remembered or chosen by its own language/default rules, so retain both, even in a different/unknown language or for image/forced subtitles. This can retain a server-selected image track that requires burn-in; honoring the per-item selection takes precedence over the text-first fallback. System captions fill a missing selection, rather than replacing the server selection. On Jellyfin 12, remembered Off is -1 and a computed no-default is null/omitted; do not collapse those values before this decision. Do not add a competing per-device remembered-choice store: the server is the cross-client authority. Reopening without a new panel choice still has automatic report provenance under PLAY-20, and omits the subtitle index in reports; accepting the server default is not a fresh explicit viewer choice. `caption-index` vectors define retention and fallback for all platforms.
