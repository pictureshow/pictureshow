# Downloads and offline (launch draft)

**Status: required launch scope. Android implemented and qualified on 10.10.7, 10.11.11 and 12.4 (`tools/launch-fixtures/offline-contract.py`); album, track and playlist downloads arrive with music. Web and Apple not implemented yet.** Apply [shared rules](shared.md), [queue/ownership rules](session-control.md) and [exact API/version boundaries](launch-api.md). Sources inspected 2026-11-03: [Plex Downloads](https://support.plex.tv/articles/downloads-overview/) describes permission-controlled personal-media downloads and original/lower quality on supported apps; [Jellyfin Android download behavior](https://github.com/jellyfin/jellyfin-android/tree/master/app/src/main/java/org/jellyfin/mobile/downloads) is behavioral evidence only. No GPL implementation is incorporated.

## What every native port must copy beyond the vectors

The vectors freeze the reducers. These behaviours live in each platform's engine, were all found by failing on real devices or by review, and aren't in a vector because they depend on time, process or the OS:

- **Failed means the server said so.** After the retries of one attempt, ask the server for the item. It answered (even an error status): the download failed, Retry is offered. No connection: wait for network, with the partial kept. A body that doesn't parse as the server's answer (a captive portal or proxy): also wait; that isn't this server.
- **A sign-in page isn't a file.** A media response with `Content-Type: text/html` is a network interruption, before anything touches the partial. An HTML 200 to a Range request would otherwise overwrite it, and an optional subtitle would save a page as a caption.
- **Rests between attempts.** A download waiting on an unreachable server rests before its next try (5 s doubling to a 5-minute cap), each download on its own timer. A real network change ends every rest at once. A callback repeating the same network answer doesn't: it changes nothing and must not restart attempts.
- **Waiting for storage rechecks itself.** Every 30 seconds, and retries only when free space grew by a margin (16 MiB here) since the denial, or a retry storm follows.
- **A revocation owed keeps being asked.** A sign-out with the server off leaves the download-set token pending; a server coming back tells nobody, so retry on a timer (60 s here) while the app runs, on any network change, and on every start.
- **One attempt's surprise ends that attempt.** Any unexpected exception becomes a failed row with plain words and Retry; cancellation passes through. Nothing in the engine's background work may take the app down.
- **Words on a failed row are plain.** Never show a raw reason code.
- **The OS-visible transfer service has a contract.** On Android: once `startForegroundService` is called the service must call `startForeground`, so never stop it while a start is unanswered, debounce the start and stop (400 ms here), and schedule the restart job only on idle to active. A refused start doesn't end the downloads' state; the scheduled job resumes them.
- **A restart stays booked while work is unfinished.** On Android a job that may run at once runs, ends and leaves the system's store, so it is gone at the kill or reboot it was for. Book it for later (2 minutes while bytes move, 15 while only waiting), book it again each time it runs, never reschedule its id while it runs, and cancel it when nothing is unfinished. Paused stays paused. If Android refuses the foreground service from the background, the job's own running time carries the bytes until its time is up. The OS decides when a booked job runs, so unattended resume is best effort, never a promise on screen: opening the app always resumes at once.
- **A truncated conversion isn't a finished one.** A chunked conversion that dies at a fragment boundary ends cleanly and indexes fine, and its hash is of the same short file. Verify adds up the fragments' durations and compares with the item's running time (`offlineConversionShort`, in the vectors): more than the larger of 5 seconds and 1% short is a failed verify, tried once more and then a failed row with plain words.
- **A blocked call must end when it's told to.** Pause and every other stop cancel the underlying request, not only the task around it, or a stalled socket keeps the old attempt alive for the whole read timeout. A new attempt waits for every earlier one on that download to end, so two can never write one partial; and an old attempt ending touches only what is its own, never the runner or reservation of the attempt that replaced it, and its network-lost report counts only while it's still the current attempt.
- **A dropped body hands back its reservation.** Otherwise a retry inside one attempt counts the remainder twice and a download close to the cap goes Waiting for storage that nobody needs to free.
- **A warm process needs waking too.** A scheduled job run in a running process must look at the network again, not only make sure the engine has started, or rows that went Waiting (the Android 15 timeout) stay there on a working network.
- **Storage full can't take the buttons away.** A refused manifest write keeps the new state in memory and in effect and is tried again, so Delete still removes bytes. Nothing a screen calls may throw at it.
- **Name the file before hashing it.** Rename the finished partial first and record it after. On a restart, a finished file the manifest doesn't know about is adopted when it can be shown whole (a conversion by running time, an Original by its validated length) and deleted otherwise, so a kill in that window costs a hash, not a conversion the server may have taken hours over.
- **A restart trusts only what was synced.** Sync the partial at every boundary (`OFFLINE_SYNC_BYTES`) before writing past it. The first resume after a restart cuts back to `offlineDurableOffset` (in the vectors): a power cut can leave a tail of the right length and the wrong bytes, and verify's hash is taken from that same file. A resume within one process keeps everything.
- **The ongoing notification names only the signed-in viewer's downloads.** Other viewers' running downloads count in the number, unnamed, on a shared device.
- **A sign-in page can't ask for a password.** Any server answer used as a yes or no (Quick Connect enabled) accepts only the server's own two answers; anything else means the server wasn't reached.
- **Sync with the viewer's newest credentials**, not the ones the progress store was made with, and a player still open at sign-out must not write the viewer's history back to disk.
- **Ask for notification permission at most once**, at the first download on touch, and a declined answer never blocks the download. TV doesn't ask.
- **Saved films come first when the server is out of reach.** With a network but no server, and ready downloads for this viewer, Home's error reads "Could not reach the server. Your downloads still play." with Watch downloads first and Retry second. With no network at all, the cold start still goes straight to Downloads.
- **The password form follows the job, not only the flag.** A download failed with `needs-password` shows the form and offers Delete rather than Retry, even after a restart or a network error has cleared the in-memory flag. Retry can't succeed without the password, and a form with no field can't be answered.
- **Tracks not downloaded are summarised in words.** "Not downloaded: Spanish audio; English, Spanish and French subtitles", each language once, from the stored language and type; tracks with no language are counted. Stored raw labels stay available to other features.
- **The mobile data override is offered only on a metered network.** On no network it does nothing, and on a TV it reads "Use this connection" with "Waiting for Wi-Fi or Ethernet". First focus never lands on it, so an OK on arrival can't spend metered data.
- **TV first focus on Downloads:** the password field, else a notice that the server's place was kept (its OK, with the whole card on screen), else the first row's primary action (a ready list's OK plays), else Storage. Back from the player goes to the row it left from, unless there's a notice: that goes first, whole, because a viewing's sync is the usual way one appears, and its OK then returns to the row. Once the viewer presses a key, later list changes don't move focus, unless the focused control went away.
- **TV focus after a delete question:** Cancel and Back return to that row's own Delete. Asking about another row moves the one question there, with focus on its Cancel. Delete moves to the row that takes its place, else the row above, else Storage, and never via the top of the page. A notice's OK moves on to the next notice, else the first row.
- **The current storage limit is always a selected option**, even when it isn't one of the steps, and deleting everything is its own group.
- **The offline player keeps the file's real duration**, from the local index, not the server's item length: 5:59 for a 359.875 s file of a "6:00" item.
- **The reconnect offer (OFF-05).** Local playback runs behind the offer and declining, by any route, changes nothing. No network is answered without a request; otherwise ask the server: same viewer, playback allowed, the source still holds that index with that type and language (`offline-reconnect`). A connection the Wi-Fi-only setting would refuse is still offered, because that setting governs downloads, not streaming; a metered network is named in the offer. Accepting runs in this order: hold playback; seal local reports while writing the last position; bring that one item's outbox record to the server, read first as always; dismiss any conflict the server kept, since the online session that starts now supersedes it; close the local session; open the online player at that position with the picked track, the other track type as the viewer had it (explicit subtitles Off included), bound to the downloaded source. The seal is the trap: a report landing after the settle would start a new record with a stale base, and the device would see its own write as a conflict. A closing session reports nothing after the seal, so it can't mark Played. Saving the place has one overall limit (15 s here), covering a wait for a background sync's lock and every call; passing it counts as a failure, and a write whose answer never came is read first as always. Failure or a change of mind before the move reopens local viewing and resumes it unless the viewer had paused. An app going to the background during the handoff says no without restarting playback. The local player leaves the back stack, so Back from the online player lands on Downloads, and a process restored into it returns there too. When the online session stops, read the item's user data into last-known state, or the next local viewing resumes from before it and sees its progress as a conflict.
- **What follows a local viewing (OFF-11).** A local player is bound to one file, so the next title opens its own local player, resuming from its own position, or the viewing ends. A server that answered decides what's next; only a ready download of the episode it named follows (`offlineNextEpisode`, vectors `offline-next`), so an episode that isn't here is never skipped. With no answer, only the next number in the same season follows, because the manifest doesn't know how long a season is. Next not downloaded: the viewing ends and returns to Downloads. It doesn't stream: OFF-11 keeps a change of source deliberate, and the server's offer is for a track the viewer picked. A controller's Next follows the same rule. The downloads are read again when the title ends, so an episode that finished downloading during this one follows it.
- **Viewing online here teaches the download.** When an online viewing of a title that's also downloaded stops, read the server's position into last-known without making the viewer wait, so the next local viewing starts there and doesn't report this device's own viewing as a conflict. That viewing is newer than anything the device still holds: a conflict's notice goes, and an unsent place goes unless the server didn't move (`offline-outbox`, `online-viewing`). A conflict's place is never a resume point: the notice says the server's was kept, and the next viewing's base is the server's, so starting from the older place would write it over the newer one (`resume` cases). The read proves the viewer first, as a sync does, and takes an answer only with both the position and the played flag: another viewer behind the same URL, a failed check or an incomplete body leaves everything held untouched.

Known limits of the Android launch implementation, which a port may do better but must not contradict: a change made elsewhere (another device's viewing, marking watched online) stays unknown until the next sync and then shows as server progress kept, because it isn't read ahead of time; with no server, the end of a season stops even when the next season's first episode is downloaded; auto-clean is a manual preview and delete, with no continuous mode offered (OFF-06e's default of off holds); image subtitles aren't available in a converted download; the server's default media source is the one downloaded; only text captions are saved as files; on Android 12 and later a download resumed in the background has no ongoing notification, because Android refuses the service there; a conversion cut off by the end of a job run restarts from zero.

## Planned vectors and proof

`offline-job` (all state transitions, duplicate callbacks, death/restart, canceled late success); `offline-budget` (exact bytes, reservations, unknown totals, concurrent final chunks, cap change); `offline-resume` (206/200/416, ETag change, truncated/corrupt resource); `offline-manifest` (atomic ready, tracks, eviction, schema upgrade); `offline-outbox` (base equals/differs with server-wins/private conflict record, dedicated download-set token lifecycle, explicit unplayed, repeated write, unknown acknowledgment, cross-account denial).

Native proof requires airplane-mode cold start and full decode/seek/end from local media. Test Original first, then finite converted video/audio with two track choices, interruption/range resume, low storage, removed account and server-wins reconnect conflict on isolated 10.10.7, 10.11.11 and 12.4; household 12.0.0 remains unchanged acceptance server. In 84B measure zero unexpected transcode restarts for sequential fetch and compare framework fetch patterns (Apple controls its own); inspect Apple packages for retained auth. Conversion stays a launch blocker. Web proves permitted original-file save, denied save, completion/cancel/interruption and external-file privacy. tvOS records OFF-PD03, not a transfer pass.
