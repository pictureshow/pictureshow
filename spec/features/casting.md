# Casting and output routes (launch draft)

**Status: required launch scope. Android sender implemented on Google's Default Media Receiver with reducer, session and reattach vectors, not device-qualified: no claim here rests on a real receiver yet. Implemented: discovery on demand, handoff, attach and reattach, Disconnect/Stop/Play here, reports on the receiver's behalf while attached, the temporary session of CAST-13. Blocked on Cast application registration (operator decision, CAST-10): the custom Web Receiver, its own report owner (CAST-03), its own sign-in (CAST-06) and Cast Connect (CAST-12). Not built yet: music (CAST-08), audio track switching, volume UI, lock-screen controls.** **Reports (temporary decision):** until a registered receiver can report for itself, the sender reports on its behalf while attached, under the receiver's session; while detached nothing reports, and that gap is accepted and visible. **Sender API:** Android uses RemoteMediaClient behind its own seam, not Media3's RemoteCastPlayer, because Google lists Media3 Cast in maintenance mode. Use [shared controls/queue](session-control.md), [API reference](launch-api.md) and APP/PLAY acceptance. Evidence: [Jellyfin web Cast configuration](https://jellyfin.org/docs/general/clients/web-config/) documents Google resources; [Plex controller/receiver support](https://support.plex.tv/articles/203082707-supported-plex-companion-apps/) documents sender/receiver intent with client-version caveats. Pictureshow improves destination clarity, privacy, handoff recovery and truthful report ownership.

| ID | Behavior | Acceptance criteria |
|---|---|---|
| CAST-01 | Play on chooser distinguishes This device, Jellyfin sessions, Google Cast and native AirPlay routes. | Device name, transport, active title/viewer if authorized and connection state are readable. Discovery does not autoplay. No-target, denied permission, unavailable SDK, unreachable server and unsupported media have different recovery. Same-named devices remain distinguishable without exposing network addresses. |
| CAST-02 | Chromecast transport and media are independently qualified. | Pass requires CAST-02a through CAST-02d individually, on an actual receiver. |
| CAST-02a | Transport operates on the selected receiver. | Start/resume, desired Pause/Play, seek and Stop match observed receiver state and CTRL-04 confirmation. Advertised volume/mute works; absent capability disables it with reason. |
| CAST-02b | Receiver negotiates its own media. | Use actual receiver formats/decoder, never the phone profile. Qualify direct, remux and transcode fixtures; show actual method/title/position. |
| CAST-02c | Receiver resources and track changes work. | Fetch captions/art/init/segments through receiver-reachable authorized URLs with correct CORS. Changing supported audio/subtitle tracks preserves pause/position; unavailable track cannot appear selected. |
| CAST-02d | Queue continuation preserves identity. | Duplicate entries, repeat/shuffle and natural EOS continue once with stable queue-entry mapping; reattaching sender reads authoritative receiver order. |
| CAST-03 | Sender-to-receiver transfer preserves viewer-selected title/position/queue. | Follow CTRL-03. Pause local output before remote starts; on failure expose Resume here. On successful transfer, receiver is sole report owner and tracks progress with its account-specific device identity. Sender reconnect displays receiver's live state, not an old local clock. |
| CAST-04 | Disconnect, Stop casting and Play here have distinct meanings. | Pass requires CAST-04a through CAST-04c individually; sender loss cannot make controls permanently unusable. |
| CAST-04a | Disconnect detaches controls. | Receiver keeps playing/reporting with a visible explanation; sender may reattach to current state. |
| CAST-04b | Stop casting ends the remote viewing. | Observe stopped state, stop reports/resources, then revoke its unused receiver token. A lost Stop acknowledgment remains Unknown, keeps the session until the viewer chooses (the receiver may still be fetching with it) and preserves cleanup status; choosing to play here anyway revokes it. |
| CAST-04c | Play here returns deliberately. | Request remote Stop and return at observed position with original pause intent. If remote Stop is unconfirmed, disclose possible double output and require explicit choice before local Play. |
| CAST-05 | Receiver can reach media independently. | Receiver fetches each manifest/segment/subtitle/artwork through a configured reachable base. Sender-only VPN, loopback forward, self-signed certificate, blocked HTTP/mixed content, CORS or local-network permission produces a specific explanation. No automatic public exposure, cloud relay or third-party CORS proxy. A server address working on the phone proves nothing about receiver access. The URLs the receiver gets carry only the CAST-13 session, never the viewer's token. |
| CAST-06 | Custom Web Receiver authenticates as the intended viewer with a bounded session. | Use its own Quick Connect device session; send the code only to the requesting Cast senderId, never broadcast. Bind request generation, server identity and expected viewer; after authorization compare returned User.Id before loading and reject/logout mismatches. Stable receiver/server/viewer DeviceId and CTRL-11 cleanup prevent session/device accumulation. Stop/end/viewer change revokes unused receiver tokens; controller Disconnect retains an actively used receiver session until playback ends. Disabled Quick Connect shows supported receiver sign-in or Jellyfin-session alternative. Never forward sender password/admin key; query-token exposure follows CTRL-10. |
| CAST-13 | A receiver without its own sign-in reads media under a revocable session, not the viewer's. | Before the load, the sender approves a Quick Connect session for the receiver with the viewer's token, under a DeviceId stable per sender/receiver/server/viewer and never the viewer's own: logging in under the viewer's DeviceId logs the viewer out. Negotiation, media and subtitle URLs and reports use only that session. It is durably recorded before use and revoked at Stop, a receiver ending it, failed/timed-out/cancelled load, foreign media, Forget, viewer change and sign-out, under CTRL-11; Disconnect, a lost link and an unconfirmed Stop keep it. Offline revocation stays pending and blocks a new session for that identity. Sign-out and account change also stop the receiver: revoking alone doesn't stop a file the server serves without a token. **Quick Connect off:** don't cast; say why and how to fix it. Never fall back to the viewer's token. Vectors: `cast-session`. |
| CAST-14 | A receiver's status is never trusted. | Anything on the receiver's network can read and write its media status, so reattach compares it with a private record written at load (random nonce, item, source, play session, per-item URL without query, route, generation) and reports only from that record. Any mismatch or missing value on either side is foreign: read-only, no controls, no reports. This hardens but doesn't authenticate: everything compared can be read and replayed. Only a receiver of ours can do better. Vectors: `cast-session`. |
| CAST-07 | AirPlay uses native media routing and retains the originating viewing. | Route chooser opens on explicit action, label reflects actual external playback and disconnect restores deliberate intent. Seek/tracks/subtitles and music lock controls are tested with an actual receiver. Do not create a second Jellyfin session/report stream solely for AirPlay output. Screen mirroring alone is not evidence of remote media playback. |
| CAST-08 | Cast works for music and recorded video; Live TV uses its real live window. | Music queue, metadata, repeat/shuffle survive sender recreation. Live tune/Stop closes owned live resources; unknown duration is Live, not zero-length VOD. Cast of private local downloads is unavailable unless a separately qualified route truly carries them; no hidden LAN file server. |
| CAST-09 | Third-party SDK loading and discovery are viewer-controlled. | Explain Google Cast before enabling its web loader; disabled mode makes no Google SDK requests. Local network refusal keeps local playback and Jellyfin session remote usable where server access exists. Revoke/disable ends discovery and stops reconnect attempts; it does not silently stop active remote media. |
| CAST-10 | Cast Connect native receiver and custom Web Receiver share one registered Cast application. | Native Android TV/Google TV app handles same-viewer Connect launches under CAST-12; plain Chromecast and rejected native launches use custom Web Receiver. One $5 developer registration covers both, pending operator answer; do not buy/register. Default Media Receiver is the $0 proof path until approved and proves only reachability/media, not custom auth/queues/reporting/Connect. Do not borrow another app's ID. |
| CAST-11 | Every platform can use authorized Jellyfin sessions even when an OS casting protocol is unavailable. | Do not substitute screen mirroring or OS D-pad control for the server session protocol. For unsupported Cast/AirPlay sender roles, chooser explains the native-platform alternative; record the exact PD row in the release matrix. No omission is called an implemented sender. |
| CAST-12 | Cast Connect launches the installed native TV app only for the same signed-in viewer. | Sender advertises androidReceiverCompatible and passes CredentialsData binding server/viewer/request generation. Native LaunchRequestChecker rejects missing, stale, malformed, different-server, signed-out or different-viewer credentials and falls back to Web Receiver. Verify expected identity against server-authenticated session state before loading, not a trusted arbitrary user-ID string. Matching viewer uses native app's own token and accepted player; no sender bearer token transfer or second report owner. Qualify same-viewer, signed-out and mismatch fallback on Android TV/Google TV. |
| CAST-15 | Play on a Cast device while one is already casting does what the viewer means, and never leaves two viewings or an unowned one. A sender holds one viewing. | Same receiver, same item: no reload, the controls show. Same receiver, another item: the old viewing's last report, encoder and session end, and the new one loads on the same link with no second join. Another receiver: the old one stops and its session ends, then the new one joins, once the old session has gone or after 3 s. Detached from that receiver, same item: reconnect. Detached, another item: reconnect first, then replace once the receiver has answered, so failing to reach it costs nothing and the viewing keeps its way to end it. Detached and picking another receiver: refused with the way forward, because stopping the old one means joining a device another app may have taken. Mid-handoff, while stopping or with the link suspended: refused with a reason, and what's already on its way is unchanged. `cast-handoff` `pick-*`. |
| CAST-16 | A connect that never succeeded isn't a lost connection. | It has its own state and message ("Couldn't connect to the device, make sure it's on and on this Wi-Fi"); the platform's error code goes to the log, not the viewer. A route already gone fails at once rather than at the 30 s limit. A reconnect that can't connect says so and keeps the viewing. `cast-handoff` `link-failed-*`. |
| CAST-17 | One empty status isn't the end of a viewing. | A status with no media and no idle reason can be an SDK that hasn't synced yet, so the sender asks again and keeps what it has; a second one ends it, and an empty status carrying a reason ends it at once. A reattach and a rejoin-to-stop follow the same rule. With no further answer a reattach offers the viewing with a way to end it and stops nothing. `cast-handoff` `*-empty-*`, `cast-session` `reattach-*-empty-*`. |
| CAST-18 | Ending a viewing never harms a newer one, and no temporary session is left behind. | The device id is stable per receiver, so a late end for an older viewing can find the newer viewing's record: it's reported as stale and changes nothing. The viewer leaving (sign-out, viewer change, forget) acts on whatever is stored. A new session waits for the old viewing's last report and revocation. A session with no viewing that refers to it is revoked at the next start. On logout, 401, 403 and 404 settle it: nothing changes by asking again and the next login under that device id replaces any token left; anything else stays pending and refuses a new session for that identity. `cast-session` `a-late-*`. |
| CAST-19 | Turning Cast off holds at sign-out too. | Sign-out with Cast off revokes the session and joins nothing. A receiver playing a file it can fetch without the token keeps playing; the viewer chose to keep this app away from Cast devices. |
| CAST-20 | Ending a viewing from its screen returns to where the viewer was. | Stop, Close and Forget never land on an empty device page. |

## Planned vectors and proof

`cast-handoff` (all owner states, local pause before remote output, receiver READY/failed/load timeout, unknown Stop, sender death/reattach); `cast-capability` (GMS absent, browser unsupported, unavailable track/volume, live window); `cast-auth` (viewer mismatch, server base-prefix, canceled/revoked Quick Connect, receiver-only auth, wrong-sender authorization rejection/logout, addressed senderId only, stable identity reuse, logout-on-end/viewer change, pending offline revocation and no server device/session accumulation, Connect same-viewer launch and mismatch/signed-out fallback, token redaction); `cast-queue` (repeat/shuffle/duplicate entry transfer). Device test: compatible original, audio-only remux, full transcode, captions, music queue, receiver shutdown, sender lock/death and VPN-only server failure. Default receiver tests never substitute for custom receiver qualification.
