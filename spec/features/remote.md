# Phone as remote for a TV session (launch draft)

**Status: required launch scope, not implemented/verified here.** Use [shared control](session-control.md), [API contract](launch-api.md) and APP/PLAY focus/recovery. Evidence: Jellyfin `SessionController`/OpenAPI provides target control; [Plex Companion](https://support.plex.tv/articles/203082707-supported-plex-companion-apps/) explains separate controller/receiver roles and warns that the article excludes new mobile versions. The design preserves the intent and adds clear target identity, permission feedback and reconnect status.

| ID | Behavior | Acceptance criteria |
|---|---|---|
| REM-01 | Phone/tablet/web Play on lists authorized active TV/client sessions through the signed-in server. | Query controllable sessions for this viewer, then filter real capability. Show target/viewer and active title only when authorized. No same-Wi-Fi requirement is invented: both endpoints need their Jellyfin connection. A TV that is asleep, signed out or disconnected is unavailable, with Open Pictureshow on TV guidance. |
| REM-02 | TV advertises supported media/commands and receives Jellyfin WebSocket Play, Playstate and GeneralCommand messages. | Fresh target capability registration follows sign-in/reconnect; receiver validates access, IDs, command shape and generation. Play resolves item as target viewer with its own device profile. A controller cannot cause target to use its own higher-privilege account or token. Unknown/unsupported commands receive safe failure/refresh, never arbitrary OS input. |
| REM-03 | Browse on phone, Play now/resume on TV, Play next and Add to queue. | Phone stays a controller; no local decoder/report starts. Queue mutations obey QUE rules and uncertain dispatch handling. Confirm actual target title/position before showing Playing. Receiver uses its own server resume unless the controller deliberately supplies a validated position. |
| REM-04 | Remote transport offers pause/play, bounded seek, previous/next, Stop and supported track/volume controls. | Buttons reflect observed state. Repeated Pause stays paused; no automatic retry of PlayPause/relative seek. Selected audio/subtitle provenance belongs to receiver viewing. Unsupported fixed-volume/track modes have reason, not a dead slider. |
| REM-05 | Optional D-pad/text remote controls Pictureshow UI only. | Advertise MoveUp/Down/Left/Right, Select, Back, GoHome and SendString only when implemented. Held navigation has bounded repeats and stops on disconnect. Text goes only into target's active non-secret editable field with length/character validation; passwords/Quick Connect fields reject remote typing. Never inject Android shell keys or gain OS/system-settings control. |
| REM-06 | Attach/refresh/disconnect/reauthorize have explicit states. | Match current server session ID as well as device identity; a restarted TV's old session cannot receive queued input. Commands expire after 5 s and never replay after reconnect. Refresh can discover the new session, but requires deliberate reattach before changing it. Disconnect phone leaves playback; Stop stops. |
| REM-07 | Household permissions remain server-authoritative. | Same-viewer, shared-device and other-user rights are distinct (`EnableSharedDeviceControl`, `EnableRemoteControlOfOtherUsers`). Explain denial without displaying restricted media or usernames not supplied by authorized API. Account switch/sign-out immediately detaches remote controls. Pairing/login Quick Connect is not unrestricted remote authorization. |
| REM-08 | Controller/target recovery works across lifecycle and SyncPlay. | Phone lock or rotation retains target safely without keeping an unnecessary local player alive. Background browser may lose connection; foreground refreshes before enabling control. TV in SyncPlay forwards transport to group; leaving group is explicit. Target Stop/exit clears remote current state and UI without a stale resume command. |
| REM-09 | All first-wave platforms can receive their supported controls while their app is available. | Android TV/Fire, Apple TV and open web TV presentation accept the shared protocol; mobile apps can also be selected when configured. Local receiver toggle defaults to permitted same-viewer control and can disable advertised commands. Server policy remains the ceiling. No wake-on-LAN, HDMI-CEC power or OS keyboard pairing is promised. |

## Platform-dependent rows

| ID | Platform-dependent limit | Acceptance and fallback |
|---|---|---|
| REM-PD01 | Android/Fire TV process session and Apple TV native session need a running, signed-in app. | A sleeping/disconnected target is unavailable; offer opening Pictureshow. No OS power/wake promise. Local volume/control rights are measured. |
| REM-PD02 | Web target can be suspended or closed; native controller can also lose its socket while backgrounded. | On return obtain fresh capabilities/session/state before enabling commands. No command replay to a restarted target; show reconnect rather than confirmed playback. |
| REM-PD03 | UI D-pad/text is Pictureshow navigation, not an OS remote service. | Advertise implemented command names only; text rejects secret/no-active-field destinations. Unsupported commands retain transport controls and local physical-remote guidance. |


Android targets collect messages outside individual Compose screens and route into one lifecycle-aware reducer; touch controller uses ordinary server networking. Apple uses a shared session service/URLSessionWebSocketTask and SwiftUI routing, not OS remote-app entitlement. Web uses authenticated WebSocket and semantic D-pad/buttons; an open/foreground tab can be a target, a closed tab cannot. Native media keys/reader input remain local input to the same reducer. No new cloud service, Google account or Cast registration is required for this subsystem.

## Planned vectors and proof

`remote-targets`: rights combinations, stale session/device, unsupported commands, same name, account changes; `remote-wire`: exact query vs JSON payloads, ticks, malformed/oversize text and secret-field rejection; `remote-receive`: duplicate messages, held key, late Play after account change, pending receiver preparation; `remote-reconnect`: dispatched versus confirmed, unknown mutation, new session and expired input.

Two clients on isolated 10.10.7, 10.11.11 and 12.4 servers, with unchanged household 12.0.0 acceptance prove browse→TV play, pause/seek/Stop, queue, UI D-pad/text, rotation/lock, TV restart, revoked rights and a different user's inaccessible title. Use emulator/simulator pairs first; final physical phone→household TV and phone→Apple TV with their real remotes/readers are separate required checks. A received HTTP 204 is insufficient evidence.
